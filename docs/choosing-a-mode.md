# 五种模式怎么选

选错模式是接入 dtmrs 最大的坑，比写错代码严重——**代码写错会报错，模式选错会静默地数据不一致**。

这篇给一套能直接照着走的判断流程。

## 30 秒决策

```
你的每一步操作，业务上能不能写出「撤销」动作？
├─ 不能（比如已经发出去的短信、已经调用的第三方支付）
│   └─ 用 msg（二阶段消息）：只保证最终送达，没有回滚
│
└─ 能
    ├─ 所有参与方都是你自己的数据库，且能接受全程持锁
    │   └─ 用 XA：强一致，中间态对外不可见
    │
    ├─ 中间态被别人看到会出事（比如超卖）
    │   └─ 用 TCC：try 阶段先冻结资源，中间态不可见
    │
    ├─ 步骤要到运行时才知道（依赖上一步的返回值 / 有 if 分支）
    │   └─ 用 workflow
    │
    └─ 其它——大多数场景
        └─ 用 SAGA
```

**拿不准就用 SAGA。** 它接入成本最低、约束最少，绝大多数业务够用。

## 逐个说

### SAGA —— 默认选它

提交时一次性给出所有 `(正向, 补偿)` 对，TC 顺序执行；任一步明确失败就逆序补偿。

| | |
|---|---|
| 适合 | 订单、履约这类可以「做了再撤」的长流程 |
| 不适合 | 中间态被看到会出事的场景（见下面「超卖」那段） |
| 代价 | **中间态对外可见**——扣了款还没发货的那一刻，别人能查到 |
| 必须 | 业务侧接[子事务屏障](integration.md)，因为分支一定会被重复调用 |

```bash
curl -XPOST localhost:36789/api/dtmsvr/submit -d '{
  "gid": "order-1001",
  "steps": [
    {"action": "http://pay/deduct",  "compensate": "http://pay/deduct-undo"},
    {"action": "http://ship/create", "compensate": "http://ship/cancel"}
  ]}'
```

### TCC —— 中间态不能被看到时用

三个阶段：`try` 冻结资源 → 全部成功则 `confirm` → 否则 `cancel`。

跟 SAGA 的区别用「超卖」讲最清楚：

- **SAGA**：直接扣库存 100 → 后面失败了再加回来。这中间别人查到的库存是少的，但钱可能没收到——业务上算「假性缺货」，一般能接受
- **TCC**：try 阶段把 100 挪进「冻结库存」，可售库存立刻减少但**没有真正扣减**；confirm 才真扣。中间态语义是明确的

选 TCC 的代价：**业务侧要多写两个接口，还要自己维护冻结态**。别为了「听起来更严谨」就上 TCC——它的接入成本是 SAGA 的两三倍。

> ⚠ **一条铁律**：TCC 的 `confirm` 返回失败**绝不会**触发 `cancel`。try 已经成功、资源已冻结、全局已决定提交，这时候 cancel 会把已确认的事务撤掉。dtmrs 的做法是无限重试 confirm + 等人介入。所以**你的 confirm 必须是能最终成功的**（幂等 + 不依赖外部易失资源）。

### 二阶段消息（msg）—— 没有回滚的那类操作

「本地事务 + 可靠消息」，取代 RocketMQ 那类事务消息，不需要 MQ。

流程：`prepare` 落库 → 业务提交自己的本地事务 → `submit`。如果进程崩在这两步之间，TC 会回查 `query_prepared` 问业务方「你那个本地事务到底提交了没有」。

| | |
|---|---|
| 适合 | 发通知、发积分、写日志、通知下游——**做了就撤不回来**的事 |
| 不适合 | 需要回滚的流程（msg 压根没有补偿分支） |
| 必须 | `prepare` 时提供 `query_prepared` 回查地址，**不给会被直接拒绝** |

为什么强制要回查地址：客户端崩在 prepare 和 submit 之间时，没有回查就没人能决断这单。猜「已提交」会重复发通知，猜「没提交」会丢单——**两种猜法都是错的**，只能问业务方。

### XA —— 强一致，但会持锁

不靠补偿，靠数据库原生两阶段提交。业务 SQL 跑完就 prepare，改动**已持久化但对外不可见**，等 TC 统一决定。

| | |
|---|---|
| 适合 | 参与方都是你自己的库、且事务很短 |
| 不适合 | 事务跨越网络调用、或者持续时间长 |
| 代价 | **全程持锁**——这是它最危险的地方 |

#### 一阶段是你自己做的，TC 只管二阶段

这是 XA 跟其它模式最大的结构差异，也是最容易误解的地方 ——
**TC 不"帮你执行两阶段"，它只负责决断和把二阶段驱动到底**：

```
业务方（RM）                          协调器（TC）
    │
    ├─ POST /prepare ──────────────────►  建一笔空事务
    │
    ├─ POST /registerBranch ───────────►  记下「有这个分支，
    │                                      commit/rollback 地址是…」
    │
    ├─ BEGIN                            ⚠ 一阶段全程在业务方这边，
    ├─ 业务 SQL                            TC 完全不参与
    ├─ PREPARE TRANSACTION 'xid'  ←──── 改动已持久化、对外不可见、锁持着
    │
    ├─ POST /submit ───────────────────►  TC 决断：提交
    │                                          │
    │  ◄──────────────────────────────────────┤ 调 /commit
    ├─ COMMIT PREPARED 'xid'                   │
    │  ─────────────────────────────────────►  收到成功，落终态
```

跟 SAGA 对照就清楚了：

| | 一阶段 | 二阶段 |
|---|---|---|
| **SAGA** | **TC 调你的 action** | TC 调你的 compensate |
| **XA** | **业务方自己做**，TC 不参与 | TC 调你的 commit / rollback |

> SAGA 里 TC 是**执行者**，XA 里 TC 是**决断者**。

TC 在 XA 里真正贡献的是业务方自己做不到的两件事：

1. **持久地记住决断结果。** 你的进程崩了重启了，那笔 prepared 事务还挂在
   数据库里等指令 —— 只有 TC 知道该 commit 还是 rollback。
2. **不放弃地重试到每个分支都确认。** `COMMIT PREPARED` 失败了 TC 会一直重试，
   **永远不会因为失败就转向回滚**（`xa_advance` 在 Submitted 阶段绝不返回
   `Finish(Aborting)`，有 3×3 种分支状态组合的穷举测试钉着）。

这也解释了为什么 **XA 的吞吐上限在你的数据库而不在 TC** —— TC 那边每笔
只多两次 HTTP 调用，重活全在数据库（见下面的实测）。

#### 什么样的参与方才能当 XA 的分支

不是"必须是数据库"，而是**必须能做真的两阶段**：

- prepare 之后改动**已持久化**（进程崩、数据库重启都不丢）
- 但**对外不可见**
- 之后**无条件服从** commit 或 rollback —— 不能反悔、不能超时自己决定

能做到的：数据库（Postgres / MySQL / Oracle…）、部分消息队列。
**做不到的**：第三方支付、发短信、调别人家的 HTTP API —— 你没法"预留一次支付"
然后挂着等。这类分支**根本不能用 XA**。

⚠ 而且**一笔事务里不能混模式**（一个全局事务只有一个 `trans_type`），
所以只要**有一个分支不能做两阶段，整笔事务就用不了 XA**。
链路里一旦出现外部服务，要么整条改用 SAGA，要么拆成两层：
内部几个库用 XA，外部调用另开一笔 SAGA / msg。

`dtmrs-xa` 只提供 **Postgres 和 MySQL** 的助手（sqlite 没有两阶段提交，
`Flavor::from_url` 直接返回 `Unsupported`）。别的资源管理器不是不能接 ——
自己实现 commit / rollback 两个端点、自己保证上面三条语义即可，
但那部分没有现成助手。

四条必须知道的约束（详见 [部署运维](deployment.md#xa-的运维红线)）：

1. **必须先 `registerBranch` 再 `PREPARE`。** 顺序反过来的话：prepare 成功了
   但登记失败 → TC 不知道有这个分支 → 那笔 prepared 事务永远没人来
   commit/rollback → **永久持锁**。这是 XA 最危险的失效模式
2. **没解决的 prepared 事务会永久持锁**，Postgres 上还阻塞 VACUUM。必须监控
3. **各分支必须操作不相交的数据**——一个分支对应一个资源管理器
4. Postgres 的两阶段提交**默认是关的**（`max_prepared_transactions=0`），要先开。
   而且这个值**直接限死在途并发**：设成 32 就最多 32 笔事务同时处于 prepared，
   第 33 笔只能等。压测时我们另起了一个设成 2000 的实例才测得动 ——
   生产上这个值通常也不大，等于 XA 的并发有个数据库层面的硬上限

> 拿不准就别用 XA，用 SAGA。XA 出问题的后果（整库不可写）比 SAGA（数据不一致）严重得多。

### workflow —— 步骤要运行时才知道

前四种都要求**提交时就把步骤声明清楚**。workflow 让你把流程写成一个普通函数：

```rust
tc.workflow("下单", |mut wf| async move {
    let oid = wf.branch("建订单").on_rollback("local://取消订单")
        .run_with(|| async { (BranchResult::Success, new_order_id()) }).await?;

    if need_ship(&oid) {                       // 真的控制流
        wf.branch("发货").on_rollback("local://退货")
            .run(|| async { ship(&oid).await }).await?;
    }
    Ok(())
})
```

崩溃后从头重放该函数，已成功的分支不重跑、直接还回上次存的返回值。

| | |
|---|---|
| 适合 | 有 if / 循环 / 依赖上一步返回值的流程 |
| 限制 | **只能在嵌入式形态下用**——「步骤」是代码，没法存成 URL |
| 要求 | **函数必须是确定性的**（见下） |

> ⚠ 重放是**从头再跑**，所以分支之间的代码会执行多次。它们必须在相同的分支返回值下走相同的路径。`if rand()`、读会变的全局状态、在分支外面直接写库——都会让重放走岔。
>
> 写岔了 dtmrs 会**当场发现并停下**（对比每个位置记录的分支名），而不是静默补偿错对象。这时候既不落成功也不回滚——那时已经不知道真实进度，硬回滚更危险。

## 实测吞吐（以及为什么它们不能直接比）

同一台机器（20 核 i7-12700）、Redis 存储、Rust 压测客户端，两万笔取中位数：

| 模式 | 吞吐 | 业务分支做了什么 |
|---|---|---|
| SAGA（2 步） | 36873 笔/秒 | **零操作** HTTP |
| msg（1 步） | 30491 笔/秒 | **零操作** HTTP |
| XA（1 步） | 8853 笔/秒 | **真的两阶段提交到 Postgres** |

### ⚠ 别读成「XA 慢 4 倍」

前两行的业务分支什么都不做，所以数字基本只反映**协调器 + 存储**的开销。
XA 那行不一样 —— 它的一阶段**就是数据库操作**
（`BEGIN` → 业务 SQL → `PREPARE TRANSACTION`，二阶段是 `COMMIT PREPARED`），
把它掏空就不是 XA 了。所以 8853 里**包含了整个数据库的开销**，另外两个不包含。

正确的读法是：

> **SAGA / msg 的上限在协调器，XA 的上限在你的数据库。**

换句话说，如果你的业务分支本身要花 10ms（真实业务基本都这样），
SAGA 那个 36873 你一笔也拿不到 —— 瓶颈会立刻变成你自己的业务逻辑。
这张表真正回答的问题是「**协调器会不会成为你的天花板**」，
对前两种模式，答案是不会。

### 一个压测时踩到的坑，用 XA 的人也会踩

第一版 XA 压测报告 **5000/5000 全部落终态**，实际业务表里**一行都没有**。

原因：一阶段的 SQL 写错了（占位符没适配 Postgres），全部静默失败；
而 XA 的二阶段 `COMMIT PREPARED` 对**不存在的 xid 是「找不到就算成功」**
—— 这在状态机保证下是正确行为（`xa_advance` 在 Submitted 阶段永不转向回滚，
所以"找不到"只可能是之前已提交），但它意味着：

> **一阶段全军覆没时，TC 侧看起来 100% 成功。**

所以用 XA 时，**光看 TC 的终态不够**，要另外核对业务库里的数据。
压测工具现在会同时报「业务库实际写入行数」和「残留 prepared 数」，
对不上就直接判这次结果作废。

复现：`cargo run --release -p dtmrs-bench -- --mode xa --busi-db <你的库>`

## 从 Seata 过来的：AT 模式对应哪个

**没有对应的。** dtmrs 不做 AT，这是选择不是遗漏。

Seata AT 的做法是：拦截你的 SQL → 查改动前的行 → 执行 → 查改动后 →
把两份镜像和业务 SQL 写进**同一个本地事务**（`undo_log` 表），
同时在 TC 上给受影响的行加**全局锁**（`lock_table`）。
回滚时读出镜像、比对有没有被别人改过、生成反向 SQL。

它在一致性光谱上介于 XA 和 SAGA 之间：

| | 谁写回滚 | 锁在哪、持多久 |
|---|---|---|
| **XA** | 数据库 | **业务库的本地锁，持到二阶段结束** |
| Seata AT | 框架自动生成 | 本地锁立即释放，改持 **TC 上的全局行锁** |
| **SAGA** | **你自己写补偿** | 不加锁 |
| **TCC** | 你自己写 cancel | 靠资源预留约定 |

**我们不做 AT 的三个理由：**

1. **跟跨语言冲突。** 我们的屏障是十几行、零依赖、四种语言各一份。
   AT 需要 SQL 解析器 + 方言适配 + 镜像捕获 + 反向 SQL 生成 + 驱动层代理，
   **每种语言都要重写一遍**。Seata 能做是因为它只服务 Java。
2. **全局锁会改变整个架构。** `lock_table` 是按行加锁的，TC 会从
   「无状态调度器」变成「锁服务」。我们现在的性质（无选主、无共享队列、
   按 gid 天然可分区）全都建立在没有全局锁之上。
3. **SQL 解析是填不完的坑**：批量操作、ORM 生成的怪 SQL、多表关联更新。

**那该用什么？**

- 想要「不写补偿」→ **用 XA**。语义比 AT 更强（真两阶段提交），
  代价是持锁时间长、要开数据库配置、吞吐低（见上面的实测）。
- 能接受写补偿 → **用 SAGA**，吞吐高一个量级，也不给数据库加负担。

要跟 Seata 比性能，公平的比法是比它的 **SAGA 或 TCC 模式**（同范式），
拿我们的 SAGA 去比它的 AT 是在比两种范式，不是比两个实现。

## 能不能混用

能，而且很常见：

- **一个事务里混用不同协议的分支**：`local://` / `http://` / `grpc://` 随便配
- **不同事务用不同模式**：订单流程用 SAGA，发通知用 msg
- **不能**在同一个全局事务里混用模式（一笔事务只有一个 `trans_type`）

## 选完之后

不管选哪个模式，**业务侧都必须接子事务屏障**——分支一定会被重复调用（TC 重试 + 崩溃恢复）。见 [业务侧接入指南](integration.md)。
